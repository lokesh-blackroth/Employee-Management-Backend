# Redis Cache Design — Department Summary

## Day 1 — 19 October 2026

### Objective

Cache the read-heavy department employee statistics endpoint to reduce
database queries and improve response latency.

---

## 1. Cache Strategy

### Cached data

The cached operation is the department summary generated by:

`employees.api.reports.get_department_summary()`

The summary contains:

- Department name
- Employee count
- Average salary
- Maximum salary

### Cache backend

Django Redis cache is used through `django-redis`.

The Redis cache configuration uses:

- Backend: `django_redis.cache.RedisCache`
- Redis database: configured through `DJANGO_CACHE_URL`
- Key prefix: `employee_management`
- Timeout: 300 seconds

### Cache key

```text
department_summary:v1

The v1 suffix allows the cache key to be changed when the
cached data structure changes.
TTL
300 seconds (5 minutes)

Five minutes provides a balance between:
- Reducing repeated database reads
- Keeping department statistics reasonably fresh
- Avoiding indefinite stale data
2. Cache Read Flow
Cache hit
1. Request checks Redis using department_summary:v1.
2. Cached data is found.
3. Cached data is returned.
4. No database query is required.
Cache miss
1. Request checks Redis.
2. No cached data is found.
3. Department summary is calculated from the database.
4. Result is stored in Redis with a 300-second TTL.
5. Calculated data is returned.
Redis failure
If a Redis cache operation raises an exception:
1. The exception is logged.
2. The application bypasses the cache.
3. get_department_summary() calculates the result directly.
4. The request can still return the department summary.
This prevents Redis availability from becoming a hard dependency for
reading department statistics.
3. Cache Invalidation Rules
The department summary becomes stale when employee department-related
data changes.

The current implementation invalidates the cache after:
- Employee creation
- Employee update
- Employee deletion
- Employee transfer
The invalidation operation deletes:
department_summary:v1

The next read therefore becomes a cache miss and regenerates the
department summary.
4. Invalidation Matrix
Operation	Cache invalidated	Reason
Employee create	Yes	Employee count/statistics can change
Employee update	Yes	Department or salary statistics can change
Employee delete	Yes	Employee count/statistics can change
Employee transfer	Yes	Department employee counts can change
Read department summary	No	Read-only operation
Redis failure	No	Fallback reads database directly
Cache expiry	Automatic	TTL expires after 300 seconds


5. Cache Stampede Risk
A cache stampede can occur when a frequently accessed key expires and
multiple requests simultaneously calculate the same expensive result.

The current implementation does not use a distributed lock or
single-flight mechanism.

For the current department summary workload, the calculation is small
and the risk is considered acceptable.

If the report becomes significantly more expensive or traffic increases,
a locking strategy should be considered.

Possible future approaches include:
- Redis distributed locking
- Short-lived lock around cache population
- Background cache refresh
- Stale-while-revalidate
6. Benchmark Methodology
The benchmark uses:
- 30 test employees
- 3 departments when benchmark departments are required
- 10 measurement runs
- time.perf_counter() for latency
- Django CaptureQueriesContext for SQL query counts
Three scenarios were measured:
1. Direct database calculation
2. Cache miss
3. Cache hit
7. Benchmark Results
Test environment
Dataset:
Employees: 30
Runs: 10

Results
Scenario	Median latency	Average latency	Median SQL queries
Direct database	1.807 ms	2.383 ms	1.0
Cache miss	3.327 ms	—	1
Cache hit	0.757 ms	0.781 ms	0.0


Observation
The Redis cache-hit path reduced median latency from:
1.807 ms → 0.757 ms

This is approximately a 58.1% reduction in median latency for this
benchmark run.

The cache-hit path executed zero SQL queries, while the direct database
path executed one SQL query.

The cache-miss path executed one SQL query because the summary must be
calculated before it can be stored in Redis.

These measurements are benchmark results for the local test
environment and should not be treated as production performance
figures.
8. Negative / Boundary Testing
Cache invalidation tests currently cover five scenarios.

The tests verify:
- Cache miss generates and stores data.
- Cache hit returns existing cached data.
- Explicit invalidation removes cached data.
- Redis read failure falls back to database calculation.
- Redis write failure falls back to returning the calculated result.
Test command:
python manage.py test employees.tests.test_cache_invalidation

Result:

OK

Benchmark command:
python manage.py test employees.tests.test_cache_benchmark -v 2

Ran 1 test
OK

9. Known Limitations
- Benchmark results are from a local test environment.
- The benchmark uses a small dataset of 30 employees.
- Cache stampede protection is not currently implemented.
- The cache contains one department-summary dataset rather than
  department-specific keys.
- Cache invalidation currently removes the complete department summary.
- Production performance should be measured with realistic traffic and
  production-scale data before making capacity decisions.
